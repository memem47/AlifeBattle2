# AlifeBattle v0.4 Design

## 1. Architecture

### 1.1 Structure

AlifeBattle intentionally uses a small architecture.

```text
main.py
   |
   v
 Game
   |
   +---- Agent[]
   |
   +---- spatial_grid
   |
   v
renderer

benchmark_performance.py
        |
        v
       Game
```

Main responsibilities:

| File | Responsibility |
| --- | --- |
| `main.py` | Main loop, input, delta time |
| `game.py` | Battle state and simulation orchestration |
| `agent.py` | Individual agent state and basic behavior |
| `spatial_grid.py` | Spatial partitioning and candidate lookup |
| `renderer.py` | Visualization and HUD |
| `config.py` | Simulation and rendering parameters |
| `benchmark_performance.py` | Repeatable benchmark and profiling |

The architecture favors explicit code and small modules over premature
abstraction.

### 1.2 State Ownership

`Game` owns:

```text
agents
winner
battle_finished
team_commands
```

`Game.reset()`:

1. clears the previous battle,
2. restores both commands to `ADVANCE`,
3. creates agents,
4. places both teams in their starting regions.

Commands belong to `Game`.

Agents do not know command names such as `ADVANCE` and `HOLD`.

### 1.3 Simulation Principles

Simulation behavior should be:

- deterministic when a fixed seed is used,
- independent of rendering FPS,
- minimally dependent on iteration order,
- measurable before optimization,
- built incrementally.

Position snapshots are used where a calculation needs a consistent view
of simulation state.

Rendering observes Game state but never changes it.


## 2. Agent Model

### 2.1 Agent State and Operations

Each `Agent` stores:

```text
id
team
position
facing_direction
hp
attack_cooldown
target
size_scale
```

Main operations include:

```text
is_alive()
update_cooldown()
update_facing_direction()
calculate_command_movement()
is_in_attack_range()
can_attack()
start_attack_cooldown()
take_damage()
```

The old steering-style separation implementation may temporarily remain
while v0.4 is being developed, but it is not part of the final v0.4
movement architecture.

### 2.2 Size Model

`size_scale` is the common source for visual and physical size.

```text
size_scale
    |
    +---- visual triangle dimensions
    |
    +---- physical occupancy radius
```

The default visual radius is derived from the triangle geometry:

```text
visual_radius =
    max(
        TRIANGLE_FRONT,
        sqrt(TRIANGLE_REAR^2 + TRIANGLE_HALF_WIDTH^2)
    )
```

The physical radius is a fixed fraction of the visual radius.

For the default agent:

```text
visual radius   ~= 12
physical radius ~= 8
```

This intentionally permits small visual overlap.

Future physical interaction uses:

```text
minimum center distance =
    agent.physical_radius
    + other.physical_radius
```

rather than a single global agent radius.

### 2.3 Facing and Rendering Representation

The triangle is rotated using `agent.facing_direction`.

Facing represents movement intent, not incidental displacement caused by
physical interaction.

Conceptually:

```text
command intent
      |
      +----> facing

command intent
      ↓
movement constraints
      ↓
actual position
```

For non-zero intended movement, facing follows the intended direction.

For zero intended movement, such as HOLD, the previous facing direction
is preserved.

The same `size_scale` also controls triangle and death-marker size.


## 3. Movement Design

### 3.1 Movement Pipeline

The final v0.4 movement pipeline is:

```text
team command
      ↓
base intended movement
      ↓
movement modifiers
      ↓
movement blocking
      ↓
allowed movement
      ↓
final position
```

Base movement is calculated conceptually as:

```text
direction * AGENT_SPEED * dt
```

v0.4 commands are:

```text
Red ADVANCE  -> (+1, 0)
Blue ADVANCE -> (-1, 0)
HOLD         -> ( 0, 0)
```

The movement-modifier stage is currently an extension point only.

Future features such as corpse or terrain slowdown may be inserted there.

### 3.2 Physical Blocking

Living agents provide hard non-penetration constraints.

The intended model is:

```text
intended movement
       ↓
determine maximum allowed movement
       ↓
move once
```

rather than:

```text
move
 ↓
overlap
 ↓
push apart
 ↓
repeat
```

The movement model is therefore kinematic rather than a general
rigid-body physics simulation.

Physical calculations use each pair's individual radii.

For:

```text
R = agent.physical_radius + other.physical_radius
```

and vertical distance `dy`:

```text
abs(dy) >= R
```

means the agents do not block each other's horizontal movement.

Otherwise:

```text
required_dx = sqrt(R^2 - dy^2)
```

defines their minimum horizontal separation.

### 3.3 Same-Direction Movement

Same-direction movement is resolved from front to rear.

For Red, larger X is farther forward.

For Blue, smaller X is farther forward.

Example:

```text
C -> B -> A ->
```

A's final position is determined first.

B may then occupy space vacated by A.

C may then occupy space vacated by B.

If A is blocked:

```text
C -> B -> A | blocker
```

the available movement decreases behind A and the stop can propagate
backward through the formation.

This produces queue-like following without iterative overlap correction.

### 3.4 Opposing Movement and Future Modifiers

Red and Blue must not be resolved simply by moving one team first.

For potentially colliding opposing agents, both intended movements for
the current update are considered together.

If full movement would create physical overlap, movement is limited to
the first point of contact.

Equal-speed opposing agents therefore consume the remaining clearance
symmetrically.

If one agent is holding, only the moving agent consumes the clearance.

Physical blocking is separate from soft movement modifiers.

```text
Hard constraint:
- living agents
- future walls

Soft modifier:
- corpses
- forest
- mud
- slopes
- rivers
```

v0.4 does not introduce a generic terrain or modifier framework.
It only preserves a clean extension point for such systems.


## 4. Combat Design

### 4.1 Local Targeting

Movement and combat targeting are independent.

After movement:

```text
final positions
      ↓
build spatial grid
      ↓
query nearby candidates
      ↓
filter living enemies
      ↓
exact ATTACK_RANGE check
      ↓
select nearest valid enemy
```

Attack targets do not influence movement direction.

### 4.2 Attack Resolution

An attack is valid when:

```text
attacker is alive
AND
target is alive
AND
cooldown <= 0
AND
target is within ATTACK_RANGE
```

Attacks are collected before damage is applied.

```text
collect attacks
      ↓
apply damage
```

This preserves simultaneous combat and prevents agent-list ordering from
changing results.

After attacking, the attacker's cooldown is reset.

### 4.3 Death and Battle Result

Dead agents remain in `Game.agents`.

They retain their final position but are excluded from living-agent
behavior.

They:

```text
do not move
do not attack
cannot be targeted
do not physically block
```

A future corpse slowdown belongs to the movement-modifier stage.

Battle result is determined after combat:

```text
Red alive   Blue alive   Result
yes         yes          continue
yes         no           Red wins
no          yes          Blue wins
no          no           draw
```

Once finished, normal updates stop until reset.


## 5. Infrastructure

### 5.1 Spatial Grid

The spatial grid is a broad-phase optimization.

```text
world position
      ↓
cell coordinate
      ↓
SpatialGrid[cell] -> Agent[]
```

It reduces the number of agents inspected for local interactions.

It does not replace exact geometric calculations.

Grid construction accepts position snapshots so calculations can use a
consistent simulation state.

The original grid query checks only the current and adjacent cells.

Movement blocking requires a more general search distance because the
required candidate range may depend on:

```text
agent physical radius
+ other-agent physical radius
+ possible movement during this update
```

Grid queries should therefore support a world-space search radius.

The grid cell size itself does not need to increase merely because a
query radius increases.

### 5.2 Simulation Update Flow

The intended final v0.4 flow is:

```text
Game.update(dt)
      ↓
clamp dt
      ↓
collect living agents
      ↓
update cooldowns
      ↓
snapshot positions
      ↓
calculate intended movement
      ↓
apply movement modifiers
      ↓
find blocking candidates
      ↓
resolve opposing contact
      ↓
resolve same-direction movement front-to-rear
      ↓
apply allowed movement
      ↓
update facing from movement intent
      ↓
snapshot final positions
      ↓
build attack spatial grid
      ↓
select local attack targets
      ↓
collect attacks
      ↓
apply damage
      ↓
check battle result
```

No iterative penetration-resolution loop is intended for normal
movement.

### 5.3 Performance

Performance optimization is measurement-driven.

The benchmark:

- uses a fixed seed,
- uses a fixed simulation delta time,
- excludes rendering,
- runs a fixed amount of simulation time,
- tests several army sizes,
- repeats measurements,
- reports simulation updates per real second,
- profiles a selected large battle.

Results are stored locally in:

```text
temp/benchmark_latest.json
```

Only the latest local result is required.

Performance results are not correctness tests because they depend on the
execution environment.

### 5.4 Testing

Automated tests cover important behavior including:

- initial placement,
- deterministic placement with a fixed seed,
- commands and reset,
- movement and delta time,
- size scaling,
- facing,
- spatial-grid lookup,
- attack range and cooldown,
- local target selection,
- simultaneous combat,
- death,
- win/draw logic,
- rendering.

Movement-blocking tests should additionally verify:

- allies block each other,
- enemies block each other,
- different-sized agents use individual radii,
- front-to-rear following works,
- stopping propagates backward,
- opposing contact is independent of update order,
- HOLD agents remain blocking,
- dead agents do not block,
- blocking does not change facing.

Manual testing remains important for battle readability, formation flow,
contact behavior, command response, and large-battle observation.


## 6. Evolution Policy

### 6.1 Deferred Systems

v0.4 deliberately does not introduce:

- `RETREAT`,
- left/right tactical commands,
- general Command classes,
- command queues,
- command history,
- command duration,
- multiple controllable units,
- squads,
- formations,
- morale,
- commander AI,
- terrain gameplay,
- corpse slowdown,
- pathfinding,
- general rigid-body physics,
- large-unit gameplay rules.

These should be added only when a later version actually requires them.

### 6.2 Documentation Policy

v0.4 is the cumulative documentation baseline.

The v0.1-v0.3 documents remain historical records explaining how the
project evolved.

A reader who wants to understand the v0.4 system should need only:

```text
docs/VISION.md
docs/specs/v0.4.md
docs/designs/v0.4.md
```

Starting with v0.5, version documents may describe only changes from the previous baseline.

When accumulated changes again make the current system difficult to understand without reading many versions, a later major milestone should create a new cumulative baseline.
