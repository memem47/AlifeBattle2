# AlifeBattle v0.4 Design

## Design Goal

Add a minimal command state without introducing a general command system.

Commands are owned by `Game`.

Agents remain unaware of command concepts and continue to receive only movement directions.

## Command Representation

v0.4 uses two simple command values:

```text
ADVANCE
HOLD
```

Do not introduce a Command class, enum hierarchy, command queue, or other abstraction yet.

Game stores one command for each team.

Conceptually:

```text
Red  -> ADVANCE
Blue -> ADVANCE
```
## Command State

`Game.reset()` initializes both teams to `ADVANCE`.

The command state persists between simulation updates until changed by player input.

## Movement Direction

`Game` converts the current command into a movement direction.

### Red

```text
ADVANCE -> (1, 0)
HOLD    -> (0, 0)
```

### Blue

```text
ADVANCE -> (-1, 0)
HOLD    -> (0, 0)
```

The resulting direction is passed to the existing `Agent.calculate_command_movement()` method.

Separation is added independently:

```text
team command
      ↓
intended movement
      ↓
movement blocking constraints
      ↓
allowed movement
      ↓
final position
```

Therefore, `HOLD` means zero commanded movement, not perfectly fixed world coordinates.

## Movement Blocking Model

v0.4 uses a kinematic non-penetration model rather than a force-based collision model.

Agents are not moved into overlapping positions and then corrected iteratively.

Instead, each agent first calculates its intended movement from the current team command. The movement system then limits that displacement to the distance that can be travelled without entering another living agent's occupied space.

The current v0.4 movement directions are horizontal only:

```text
Red ADVANCE  -> +X
Blue ADVANCE -> -X
HOLD         -> 0
```

This restriction allows movement blocking to be resolved in travel order without introducing a general rigid-body physics solver.

### Same-Direction Blocking

Agents moving in the same direction are resolved from front to rear.

The final position of a front agent is therefore known before the movement limit of the following agent is calculated.

This allows rear agents to move into space vacated by agents in front.

If the front agent stops, the available space becomes zero when the minimum agent distance is reached, so the stop propagates backward through the formation.

### Opposing Movement

Opposing agents must not be resolved by simply moving one team first.

For a potentially colliding pair, both agents' both agents intended displacement for the frame is considered simultaneously.

If their full intended movements would cause their physical spaces to overlap, both movements are limited to the instant of first contact.

For equal0speed opposing agents this naturally divided the remaining closing distance equally.

If one agent is holding, only the moving agent consumes the remaining clearance.

For two agents whose vertical distance is smaller than `SEPARATION_DISTANCE`, the required horizontal center distance is derived from their circular occupancy:

```text
required_x_distance = sqrt(SEPARATION_DISTANCE^2 - vertical_distance^2)
```

If the vertical distance is already at least SEPARATION_DISTANCE, the two agents do not block each other's horizontal movement.

Movement blocking requires a wider candidate search than attack targeting.

The blocking search radius must include both physical agent distance and the maximum relative displacement possible during one update.

The spatial-grid implementation must therefore support querying more than the fixed 3x3 neighboring cells when necessary.

The grid cell size itself does not need to be increased solely for movement blocking.

## Input Handling

`main.py` remains responsible for pygame input events.

On `KEYDOWN`:

```text
A -> toggle Red command
B -> toggle Blue command
R -> reset battle
```

Input handling should call a small `Game` method rather than modifying internal command state directly.

For example:

```text
game.toggle_team_command(team)
```

## Responsibilities

### `main.py`

- handles keyboard input,
- requests command changes from `Game`.

### `Game`

- owns current team commands,
- resets commands at battle reset,
- toggles command state,
- translates command state into movement directions.

### `Agent`

- does not know about `ADVANCE` or `HOLD`,
- continues to calculate movement from a supplied direction. 

### `Renderer`

- displays the current command for Red and Blue.

## Update Flow

The simulation update structure remains:

```text
update cooldowns
      ↓
snapshot living-agent positions
      ↓
calculate intended command movement
      ↓
find potential movement blockers
      ↓
limit opposing movement to first contact
      ↓
resolve same-direction movement front to rear
      ↓
apply allowed movement
      ↓
update facing from command intent
      ↓
build post-movement spatial grid
      ↓
select local attack targets
      ↓
resolve attacks
      ↓
check battle result
```

No iterative penetration-resolution loop is planned for normal movement.

Changing commands does not alter combat targeting.

## Testing Strategy

Tests should verify:

- both teams start with `ADVANCE`,
- reset restores both commands to `ADVANCE`,
- command toggling changes only the requested team,
- Red `ADVANCE` moves right,
- Blue `ADVANCE` moves left,
- `HOLD` produces zero command movement,
- separation can still move an agent while holding,
- holding agents can still attack nearby enemies.

Keyboard-event handling should be tested separately from command behavior where practical.

## Deferred Design

Do not yet introduce:

- `RETREAT`,
- a `Command` class,
- enums unless clearly needed,
- per-agent commands,
- units or squads,
- command duration,
- command history,
- command queues.
