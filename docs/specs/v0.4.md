# AlifeBattle v0.4 Specification

## 1. System Overview

### 1.1 Purpose

AlifeBattle is a real-time battle simulation in which many autonomous
agents fight as two opposing teams.

v0.4 is the cumulative specification baseline for the project.

It includes all requirements that remain valid from v0.1 through v0.4.
Earlier specification documents are retained as historical records.

A reader should not need to read v0.1-v0.3 to understand the behavior
required by v0.4.

### 1.2 Battlefield

The simulation contains two teams:

- Red
- Blue

The default battle size is:

- Red: 50 agents
- Blue: 50 agents

Red starts on the left side of the battlefield.
Blue starts on the right side.

Starting positions are randomized within each team's starting area.

A fixed random seed may be used when reproducible behavior is required
for testing, debugging, or benchmarking.

Initial placement should avoid excessive overlap between agents.

A 500-vs-500 battle is used as a stress-test workload for performance
evaluation.

### 1.3 Agent Basics

Each agent has at least:

- a unique ID,
- team,
- position,
- facing direction,
- HP,
- attack cooldown,
- attack target,
- size scale.

Default gameplay parameters are:

| Parameter | Default |
| --- | ---: |
| HP | 100 |
| Speed | 28 px/s |
| Attack Damage | 20 |
| Attack Interval | 1.0 s |
| Size Scale | 1.0 |

Agents are alive while HP is greater than zero.

Agents die when HP reaches zero.

Movement uses delta time and must not depend on rendering FPS.


## 2. Movement

### 2.1 Team Commands

Each team has one persistent movement command.

v0.4 supports:

```text
ADVANCE
HOLD
```

Both teams start with `ADVANCE`.

For `ADVANCE`:

```text
Red  -> +X
Blue -> -X
```

Agents do not search for enemies in order to decide where to move.

`HOLD` produces no commanded movement.

A holding agent remains physically present and may still fight nearby
enemies.

### 2.2 Agent Size and Physical Occupancy

Each agent has a `size_scale`.

The same scale controls both:

- visual triangle size,
- physical occupancy size.

The physical shape is approximated as a circle.

The physical radius is intentionally smaller than the maximum visual
radius of the triangle, so small visual overlaps are acceptable.

For two living agents, the required minimum center distance is:

```text
agent.physical_radius + other.physical_radius
```

v0.4 currently creates normal agents with the default size scale.

Different-sized unit types are not yet part of normal gameplay, but the
physical model must not assume that all agents have identical sizes.

### 2.3 Movement Blocking

Living agents physically block other living agents regardless of team.

A living agent must not move through another living agent.

Movement should be restricted before penetration occurs rather than
normally relying on repeated overlap correction.

For agents moving in the same direction, movement is resolved from the
front of the formation toward the rear.

A rear agent may use space vacated by an agent in front.

If a front agent cannot advance, the movement restriction should
propagate backward through following agents.

Opposing moving agents must be treated as moving simultaneously.

Neither team may receive movement priority merely because it is
processed first.

If two opposing agents would overlap during an update, their movement
is limited to their first physical contact.

Although commanded movement is horizontal in v0.4, physical occupancy
is two-dimensional and vertical separation must be considered.

### 2.4 Dead Agents and Future Movement Effects

Dead agents:

- remain at their final position,
- do not move,
- do not attack,
- cannot be attack targets,
- do not physically block living agents.

Living agents may move through or occupy a dead agent's position.

Physical blocking and movement-cost effects are different concepts.

Future versions may introduce movement penalties caused by:

- corpses,
- forests,
- mud,
- rivers,
- slopes,
- other terrain.

Such effects should reduce or modify movement rather than necessarily
making an area impassable.


## 3. Combat

### 3.1 Local Targeting

Movement and combat targeting are independent.

After movement, each living agent searches nearby agents for a valid
attack target.

A valid target must:

- be alive,
- belong to the opposing team,
- be within `ATTACK_RANGE`.

If multiple valid enemies exist, the nearest one is selected.

Global nearest-enemy search must not determine movement direction.

### 3.2 Attack Rules

An agent may attack when:

- the attacker is alive,
- the target is alive,
- the target is within attack range,
- attack cooldown is zero.

A successful attack:

- deals the configured attack damage,
- starts the configured attack cooldown.

Attacks for an update are collected before damage is applied.

This allows simultaneous combat and prevents agent-list order from
changing the result.

### 3.3 Battle Result

Red wins when no Blue agents remain alive.

Blue wins when no Red agents remain alive.

If both teams die during the same update, the result is a draw.

After the battle finishes, normal simulation updates stop until reset.


## 4. User Interface

### 4.1 Controls

Keyboard controls are:

| Key | Action |
| --- | --- |
| A | Toggle Red between `ADVANCE` and `HOLD` |
| B | Toggle Blue between `ADVANCE` and `HOLD` |
| R | Reset the battle |
| Esc | Quit |

Changing one team's command must not modify the other team's command.

Reset restores both teams to `ADVANCE`.

### 4.2 Rendering

Living agents are drawn as triangles.

The triangle:

- points in the agent's facing direction,
- scales with `agent.size_scale`,
- uses team-specific colors,
- changes color according to remaining HP.

Health is represented using three levels:

| Health | State |
| --- | --- |
| Above 2/3 | Healthy |
| Above 1/3 through 2/3 | Damaged |
| 1/3 or below | Critical |

Dead agents remain visible using team-colored death markers.

Death-marker size scales with agent size.

Dead agents are rendered before living agents so living agents may
visually pass over corpses.

Rendering must not modify simulation state.

### 4.3 HUD and Debug Display

The HUD displays:

- surviving Red count,
- surviving Blue count,
- current FPS,
- current Red command,
- current Blue command,
- battle result when finished.

The spatial grid may optionally be displayed for observation and
debugging.


## 5. Quality and Scope

### 5.1 Performance

A normal 50-vs-50 battle must remain responsive enough to observe in
real time.

Performance changes should be based on measurement rather than
speculation.

The benchmark:

- uses a fixed random seed,
- uses a fixed delta time,
- processes a fixed amount of simulation time,
- excludes rendering,
- measures multiple army sizes,
- reports simulation updates per real second,
- may profile a large battle.

A 500-vs-500 battle is used as a stress test.

Benchmark results are machine-dependent and are not automated pass/fail
tests.

### 5.2 Technical Constraints

The implementation should preserve these principles:

- simulation behavior is independent of rendering FPS,
- local interactions should use spatial partitioning where appropriate,
- candidate lookup does not replace exact geometric checks,
- different-sized agents must be supported by physical calculations,
- movement intent and physical blocking are separate concepts,
- facing should represent movement intent rather than collision side
  effects,
- unnecessary abstractions and premature optimization should be avoided.

### 5.3 Out of Scope

v0.4 does not include:

- `RETREAT`,
- left/right tactical commands,
- formations,
- multiple controllable units or squads,
- command queues,
- command duration,
- commander AI,
- morale,
- terrain gameplay,
- corpse movement penalties,
- pathfinding,
- a general physics engine,
- different-sized unit types in normal gameplay.

### 5.4 Done When

v0.4 is complete when:

- a 50-vs-50 battle runs from start to finish,
- both teams start with `ADVANCE`,
- `A` and `B` independently toggle the two teams,
- reset restores both commands to `ADVANCE`,
- Red ADVANCE moves right and Blue ADVANCE moves left,
- HOLD produces zero commanded movement,
- movement is independent of attack-target selection,
- combat targeting is local,
- HOLD agents continue fighting nearby enemies,
- living agents cannot move through living agents,
- blocking applies to allies and enemies,
- rear agents can use space vacated by agents ahead,
- blocking can propagate backward through a formation,
- opposing contact is not biased by update order,
- dead agents do not physically block living agents,
- facing is not changed by blocking side effects,
- visual and physical sizes remain related through `size_scale`,
- battle state and commands are visible,
- automated tests pass,
- large-battle performance remains measurable.
