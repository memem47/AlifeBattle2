# AlifeBattle v0.1 Specification

## 1. Purpose

The purpose of v0.1 is to create the smallest complete version of AlifeBattle.

Two groups of autonomous agents should move toward their enemies, fight, die, and eventually produce a winner.

This version is intended to establish the basic simulation loop and software structure for future versions.

The implementation should remain small enough that the entire behavior of the simulation can be understood and explained.

---

## 2. Scope

v0.1 contains:

* two opposing teams,
* 10 agents per team,
* autonomous movement,
* nearest-enemy targeting,
* simple melee combat,
* hit points,
* death,
* battle completion,
* basic graphical visualization,
* and battle restart.

No additional tactical mechanics are required.

---

## 3. Battlefield

The simulation uses a two-dimensional rectangular battlefield.

Initial conditions:

* Team Red starts on the left side.
* Team Blue starts on the right side.
* Each team contains 10 agents.
* Agents begin with some distance between the two armies.
* All agents are alive when the battle starts.

The initial positions may be fixed in v0.1 so that simulation behavior is easy to reproduce.

---

## 4. Agent

Each agent has the following state:

* team,
* position,
* hit points,
* attack cooldown,
* and alive/dead state.

All agents use identical parameters in v0.1.

Example initial parameters:

| Parameter       |   Value |
| --------------- | ------: |
| Hit Points      |     100 |
| Movement Speed  | 60 px/s |
| Attack Damage   |      20 |
| Attack Range    |   12 px |
| Attack Interval |   1.0 s |

These values may be adjusted during development.

They are configuration values rather than fundamental game rules.

---

## 5. Agent Behavior

Each living agent repeatedly performs the following behavior.

### 5.1 Find a Target

The agent selects the nearest living enemy.

The target may be recalculated every simulation update in v0.1.

### 5.2 Move Toward the Target

If the target is outside attack range, the agent moves directly toward the target.

Movement speed must be based on elapsed simulation time rather than frame count.

Conceptually:

```text
distance moved = movement speed × delta time
```

### 5.3 Attack the Target

If the target is within attack range and the attack cooldown has expired, the agent attacks.

An attack immediately reduces the target's hit points by the configured attack damage.

The attacker then starts its attack cooldown.

### 5.4 Death

If an agent's hit points become zero or less, the agent dies.

Dead agents:

* cannot move,
* cannot attack,
* cannot be selected as valid targets.

---

## 6. Simulation Update

The simulation repeatedly executes the following high-level process:

```text
1. Process input
2. Update living agents
3. Resolve movement
4. Resolve attacks
5. Remove or disable dead agents
6. Check battle result
7. Render the battlefield
```

The exact internal implementation may differ, but the behavior should remain understandable.

---

## 7. Battle Result

The battle ends when one team has no living agents.

Possible results are:

* Red wins
* Blue wins

A draw does not need to be explicitly supported in v0.1 unless both teams happen to die during the same update.

When the battle ends:

* agent simulation stops,
* the winner is displayed,
* and the user can restart the battle.

---

## 8. User Interaction

v0.1 requires only minimal user interaction.

Required controls:

* Start the program
* Observe the battle
* Restart the battle

Optional:

* Pause / resume
* Quit with the Escape key

The player does not issue tactical commands in v0.1.

---

## 9. Visualization

The battlefield should make individual agents easy to distinguish.

Minimum visualization:

* Red agents are visually distinguishable from Blue agents.
* Living agents are visible.
* Dead agents disappear or are clearly shown as dead.
* The current number of surviving agents on each team is displayed.
* The final winner is displayed.

Agents may initially be represented by simple circles.

No sprites, animation, effects, or detailed UI are required.

---

## 10. Determinism

The default v0.1 battle should preferably use fixed starting positions.

If randomness is introduced, it should be possible to provide a fixed random seed.

This makes behavior easier to debug and compare between code changes.

---

## 11. Performance Requirements

Performance optimization is not a major goal of v0.1.

The simulation only needs to support approximately 20 agents smoothly on a normal desktop computer.

Algorithms with poor large-scale performance, such as checking every enemy when selecting a target, are acceptable in this version.

Optimization mechanisms such as spatial grids should not be added until a later version demonstrates a need for them.

---

## 12. Non-Goals

The following features are explicitly outside the scope of v0.1:

* formations,
* morale,
* courage,
* retreat,
* fleeing,
* encirclement,
* directional damage,
* front / side / rear attacks,
* individual agent attributes,
* different soldier types,
* terrain,
* obstacles,
* ranged attacks,
* tactical commands,
* commanders,
* pathfinding,
* spatial grids,
* advanced collision avoidance,
* separation behavior,
* large-scale battles,
* complex GUI settings,
* save/load,
* statistics,
* artificial intelligence beyond simple local rules.

These features may be introduced in later versions.

---

## 13. Completion Criteria

v0.1 is complete when all of the following conditions are satisfied:

1. The program starts without errors.
2. Twenty agents appear on the battlefield.
3. Red and Blue agents can be visually distinguished.
4. Each agent autonomously selects an enemy.
5. Agents move toward their selected enemies.
6. Agents attack enemies within attack range.
7. Attacks reduce hit points.
8. Agents die when their hit points reach zero.
9. Dead agents no longer participate in combat.
10. One team eventually wins.
11. The winner is displayed.
12. The battle can be restarted.
13. Simulation speed is not dependent on rendering frame rate.
14. The developer can explain the complete simulation update flow.

---

## 14. Design Constraints

The implementation should favor simplicity over future flexibility.

For v0.1:

* Avoid unnecessary abstraction.
* Avoid implementing features only because they may be useful later.
* Avoid premature performance optimization.
* Avoid hidden behavior that is difficult to observe.
* Keep configuration values separate from simulation logic where practical.
* Keep simulation logic separate from rendering where practical.

The code should be easy to modify when the requirements of the next version become clear.

---

## 15. Definition of Done

v0.1 is not complete when all planned code has been written.

v0.1 is complete when the battle works from start to finish, its behavior can be observed, and the developer understands why the simulation behaves as it does.

> Twenty agents. Two teams. Move, fight, die, win.
