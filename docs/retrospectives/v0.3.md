# AlifeBattle v0.3 Retrospective

## Result

v0.3 changed the basic agent behavior from enemy-driven movement to command-driven movement.

The main changes were:

- Red agents advance to the right.
- Blue agents advance to the left.
- Movement no longer depends on the nearest enemy.
- Movement and attack targeting are separate concerns.
- Global nearest-enemy search was removed.
- Attack targets are selected only from local spatial-grid candidates.
- Only enemies within attack range can become attack targets.
- Existing separation, cooldown, damage, and simultaneous attack behavior were preserved.

## Performance

Latest benchmark results on the development machine:

| Team size | Total agents | Simulation FPS |
| ---: | ---: | ---: |
| 50 | 100 | 1047.1 |
| 100 | 200 | 610.4 |
| 250 | 500 | 235.1 |
| 500 | 1000 | 91.9 |

Compared with the previous global-targeting implementation:

| Team size | Previous FPS | v0.3 FPS | Change |
| ---: | ---: | ---: | ---: |
| 50 | 481.9 | 1047.1 | +117.3% |
| 100 | 190.3 | 610.4 | +220.8% |
| 250 | 38.2 | 235.1 | +515.8% |
| 500 | 11.9 | 91.9 | +674.8% |

The exact values are machine-dependent and are used only for relative comparison.

## Current Bottlenecks

For the 500-vs-500 benchmark, the main cumulative costs were approximately:

- `Game.update()`: 5.49 s
- `_plan_movements()`: 3.54 s
- `get_neighbor_candidates()`: 2.15 s
- `calculate_separation()`: 2.10 s
- `_select_local_attack_targets()`: 1.18 s

The previous global nearest-enemy targeting bottleneck is no longer dominant.

Further performance optimization is deferred because 500-vs-500 now exceeds 60 simulation updates per second on the development machine.

## What We Learned

- Movement and combat targeting should be separate responsibilities.
- Global nearest-enemy search was unnecessary for the intended battle model.
- Spatial-grid local search works well for both separation and combat targeting.
- Removing an unnecessary algorithm can provide much larger gains than micro-optimizing it.
- Performance profiling was useful for distinguishing structural problems from small implementation costs.
- The current fixed advance behavior is a useful foundation for explicit player commands.

## Next Direction

v0.4 should introduce the first player-controllable commands.

The initial command set should remain minimal:

- `ADVANCE`
- `HOLD`

The goal is to allow a team to switch between advancing and holding position without introducing formations, multiple units, or complex command hierarchies yet.
